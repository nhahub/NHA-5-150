# M3 Design Decisions (agreed before Milestone 3)

These decisions were agreed by the team so that Tracks 3A, 3B and 3C fit together. Anything that deviates from the project proposal (`Smart_Shelf_v5.md`) is marked **Deviation**. Decisions 4 and 5 are finalised by the data checks in M2-T12.

| # | Topic | Decision | Reason |
| --- | --- | --- | --- |
| 1 | OOF scheme for Track 3A | Time-blocked 5-fold inside the training period (2023-01-01 to 2024-08-07). Each block is predicted by a model trained on the other blocks. A stricter expanding-window variant is implemented as an optional check. Test rows and the simulator use the final model fitted on all training data. | Matches the proposal. AUC is practically the same as stratified folds (0.5870 vs 0.5859), and time-blocked probabilities are closer to deployment behaviour. |
| 2 | Feature sets | Track 3A compares two sets by Brier score and log loss under CV: **full** (the proposal's set) and **compact** (full minus features M2-T05 found to carry no signal). The winner is recorded as `feature_set_name`. Track 3B uses batch features, the OOF spoilage probability, `discount_pct` and the confounding controls. Never used as features: `spoilage_risk`, outcome columns, M2-T04 discount tier flags. Track 3A also excludes `discount_pct`, `markdown_applied`, `selling_price`. Track 3B excludes `selling_price` and `markdown_applied`. | Univariate AUC misses interactions, but extra noise can hurt calibration, the headline metric. Evidence decides. If the compact set wins, this is a **Deviation** to document. |
| 3 | Shelf-life version | `expiry_remaining_ratio` for both models. `shelf_life_used_ratio` is a single ablation run. Never both in one model. | It is the proposal's formula and what a manager types into the simulator. Both are highly redundant. |
| 4 | Track 3B target | Model sell-through s = units_sold / initial_quantity (bounded 0 to 1) and derive profit with the exact identity profit = initial_quantity x (s x selling_price - cost_price), where selling_price = round(base_price x (1 - discount_pct), 2). Checked in M2-T12: the identity holds with maximum error 0 on all 100,000 rows. Clip predicted s to [0, 1]. Report profit metrics on the original scale. | Profit has extreme tails (1st percentile -39,477, 99th percentile 44,919; 28.7% of batches lose money). Sell-through is bounded and keeps the optimizer consistent with the accounting identity. |
| 5 | Low-confidence flag | **Deviation from the proposal.** Support cell = product_name x store_id (3,150 cells, mean 25.4 training rows). Flag when fewer than 20 training rows (cells never seen in training count as 0 and are flagged), flagging 14.4% (2,866) of test rows. Deviation documented in `reports/M2/M2_T12_Decision_Checks.md`: calibration and accuracy show no measurable difference; the bootstrap intervals are wide (about +/-0.009 on the test period), so moderate differences cannot be ruled out (actual gaps: flagged +0.35 points over-prediction, unflagged -0.57 points under-prediction). The flag is sensitive to the threshold (20 flags 14.4% of test rows, 25 flags 44.6%, 30 flags 74.3%). The dashboard should word the flag as "limited history for this product at this store", not as low model confidence. One shared function in `src/support.py` is used by 3A, 3B and 3C. | The proposal's category x region x store cells (500 cells) all have at least 129 training rows, so that flag never triggers at any sensible threshold (checked in M2-T12). Product x store is the only granularity where support varies, and the models use product and store features. |
| 6 | Model storage | `models/track_3a_classifier.joblib` and `models/track_3b_regressor.joblib`, each with a JSON file beside it (ordered feature list, shelf-life version, training period, library versions, MLflow run ID). `data/` and `models/` stay gitignored; seeded scripts regenerate everything. When final models exist, ask the team to whitelist `models/final/` so the instructor can see them. | Prevents feature-order mistakes. Teammates cannot share ignored files through git. |
| 7 | Sequencing | Freeze the interface on day 1: file name and columns of the baseline OOF file. 3B works against that stub, 3C against a placeholder `predict(batch, discount)`. One named interface owner. | Lets the three tracks work in parallel. |
| 8 | Sales velocity | Keep `sales_velocity` as built: 7-day window on earlier transaction dates, category x store fallback. Document the limitation. Add a Track 3B ablation with and without it, and test the pre-sale alternative `initial_quantity / daily_demand` as a second control. | Built and validated, signal is near zero (correlation 0.007). It cannot be made strictly causal without day-level sales data. |

## Known limitation: sales velocity

In this dataset `units_sold` is a batch's lifetime total attributed to its transaction date. An earlier batch may have kept selling after the current batch's transaction date, so "sales recorded before the batch's own transaction" holds only approximately. The practical impact is small, and it must be stated in the Final Report.
